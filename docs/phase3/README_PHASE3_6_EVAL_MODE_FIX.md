# PersTSFM Phase 3.6 — evaluation-mode checkpoint parity fix

## Diagnosis

The previous audited fine-tuning run completed 100 training steps, then failed
because forecasts from the in-memory model and `finetuned-ckpt` differed by
3.8402% on the audit's max-value-scaled comparison. The Phase 3.4 backend
never explicitly switched a fitted model from `train()` to `eval()` before
forecasting. In Chronos-2, `predict()` uses `torch.no_grad()`, but `no_grad`
does not disable stochastic layers. A reloaded Hugging Face model typically
starts in eval mode, so that is a plausible (not yet confirmed) explanation.

## What's fixed

- Added `src/experiments/adaptation_benchmark/inference_safety.py`
  with `ensure_eval_mode()` and checkpoint weight diagnostics.
- The patcher inserts `ensure_eval_mode(self.adapter.pipeline)` into the
  shared `Chronos2Backend.forecast` method for both zero-shot and adaptation.
- It also forces `trained` and `loaded` into eval mode immediately before
  the strict checkpoint parity test in `fit_audited`.
- It **does not relax** the `1e-3` maximum-relative tolerance. If parity still
  fails, it saves `capability_audit_failed.json` including model classes,
  inference-mode flags, and matched parameter deltas.
- The patcher is idempotent, validates exact source fragments, backs up
  changed source under `archive/patch_backups/phase36_eval_mode/`.
- It never accesses FEV official test labels or edits any experiment result.

## Prior experiment comparability

Phase 3.3/3.4/3.5 LoRA forecasts were generated by an earlier adapter path
that did not explicitly enforce model eval mode. They should be labelled
**provisional for the LoRA-versus-zero-shot comparison** until a re-run with
this guard establishes parity. There may be no practical change if the model
was already in evaluation mode via another internal path; do not assume
an error magnitude without re-running. Zero-shot forecasts are expected to
remain unchanged, but confirm with your existing parity checks.
